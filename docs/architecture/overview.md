# 0.3 기술 아키텍처와 증거 모델

상태: 설계 초안 · 확인일: 2026-11-02 · 관련 Issue #5. 이 문서는 구현이나 실환경 검증의 완료를 의미하지 않는다. 0.2의 [선행 조사](../research/competitor-analysis.md)에서 확인한 것처럼 낭비 탐지·사용량 원장·검증 근거·팀 비교는 각각 선행 사례가 있다. 차별화와 절감 효과는 검증할 가설이다.

## 목표와 단계

첫 구현은 사용자가 지정한 기존 실행 기록을 **모델 호출 없이 읽어** 근거를 보존하는 정규화 결과와 JSON을 만든다. 품질을 유지하면서 팀 운영이 유리했는지 판단하는 기능은 후속 보고서·실험 단계에서 검증한다. 에이전트 수가 적다는 사실만으로 성공을 판정하지 않는다.

| 단계 | 범위와 산출물 |
| --- | --- |
| 1: 수집 | 지정된 기록 가져오기, 식별자 연결, 중복 처리, 불완전 상태와 JSON 내보내기 |
| 2: 보고서 | 규칙 기반 중복 탐색·위임·오류·검증 누락 후보와 근거, JSON/HTML |
| 3: 팀 선택 | 사용자가 Solo·Small·Full·Manual을 선택하고, 이후 규칙 기반 추천과 이유를 별도 표시 |
| 4: 실험 | 사용자가 명시적으로 실행한 경우에만 동일 조건의 팀 구성을 비교 |
| 5: 데스크톱 | 검증된 코어를 사용하는 Electron/React UI |
| 6: Harness² | 별도 선택형 어댑터와 개선 전후 실험; 기본 작업에서 자동 실행하지 않음 |

단계 1에서는 팀 자동 추천·모델 호출·실험 실행·데스크톱 UI를 구현하지 않는다. 한국어를 주 언어로 사용한다.

## 경계와 데이터 흐름

```text
사용자가 지정한 기록 / 공식 API의 읽기 결과
  → 어댑터(출처·버전·원본 위치 기록)
  → 정규화기(이벤트·식별자·불확실성)
  → 로컬 저장소(중복 처리·연결·가용성)
  → 규칙 분석기 → CLI JSON / 이후 HTML·데스크톱
                         ↑
       사용자 선택 팀 / 명시적 실험 실행기(후속 단계)
```

- **코어:** 데이터 모델, 정규화, 이벤트 연결, 저장 인터페이스와 내보내기를 소유한다. UI·특정 실행기·모델 공급자에 의존하지 않는다.
- **Codex 어댑터:** 버전별 외부 형식을 내부 이벤트로 변환한다. 공식 인터페이스와 지원 여부를 확인하고, 미지원 형식은 다른 버전으로 추측해 해석하지 않는다. 운영체제·WSL의 경로와 실행 방식은 이 경계에 격리한다.
- **로컬 저장소:** SQLite를 후보로 한다. 원본 출처의 식별자·수집 상태·정규화 결과를 일관되게 보존한다. 실제 의존성·버전·마이그레이션 도구는 0.4 또는 해당 구현 Issue에서 정한다. JSON 내보내기와 데이터베이스 내부 표현은 분리한다.
- **분석기:** 수집과 분리된 결정적 규칙을 적용한다. 감지한 사실과 해석을 구분하고, 근거 이벤트·규칙 버전·한계·오탐 가능성을 결과에 연결한다. 별도 LLM 호출은 하지 않는다.
- **CLI·UI:** 같은 코어 인터페이스를 호출한다. 단계 1은 CLI 중심이며 화면에서 비공개 내부 추론을 보여준다고 주장하지 않는다. 메시지 원문과 별도 복사본, 요청한 설정과 실제 확인된 값을 구분한다.
- **팀 선택·실험기:** 후속 모듈로 분리한다. 자동 추천은 초기 구현에 넣지 않는다. 실험의 모델 호출·코드 변경은 읽기 전용 분석과 별도인 명시적 사용자 동작이다.

권장 구현 언어는 TypeScript/Node.js, UI는 Electron/React, 테스트는 Vitest다. 이 단계에서는 패키지·버전·구체 파일 구조를 확정하거나 설치하지 않는다.

## Codex 연동과 관측 가능성

[공식 App Server 문서](https://learn.chatgpt.com/docs/app-server)는 `thread/read`를 스레드 메타데이터 조회로 설명하며, 저장된 turn과 item은 페이지 조회 API를 통해 읽도록 안내한다. 동일 문서는 `thread/tokenUsage/updated`를 활성 스레드의 사용량 갱신으로 설명한다. 이 사실만으로 과거 기록에 해당 알림이나 모든 하위 스레드·사용량이 남아 있다고 가정하지 않는다.

App Server는 공식적으로 수명주기와 이벤트를 다룰 수 있지만, 저장 기록 가져오기와 실시간 구독은 서로 다른 출처다. 단계 1은 **기존 기록의 모델 호출 없는 가져오기**를 우선하며 실시간 구독은 별도 구현·검증 전까지 지원한다고 주장하지 않는다. 공식 API로 필요한 기록을 얻을 수 없는 버전은 미지원 또는 부분 지원으로 표시한다. 사용자 환경의 비공식 저장 형식을 다룰 경우 별도 어댑터로 격리하고 사용자가 선택한 파일만 읽는다.

공식 문서상 `thread/list`는 `useStateDbOnly`를 생략하거나 `false`로 설정하면 JSONL을 스캔해 메타데이터를 복구할 수 있다. 읽기 전용 목록이 필요한 경우 해당 버전에서 `useStateDbOnly: true`의 지원을 확인하고 사용하며, 지원하지 않으면 미지원·부분 지원으로 보고한다. 이 옵션 하나만으로 App Server 전체에 쓰기가 없다고 단정하지 않고 실제 부작용을 별도로 검증한다. 목록의 `sourceKinds` 기본값은 대화형 출처에 한정되므로 하위 에이전트가 빠질 수 있음을 기록한다.

`thread/turns/list`의 `itemsView` 기본값은 `summary`다. 요약을 완전한 item 또는 검증 증거로 취급하지 않는다. 필요할 때 `full` 또는 `thread/items/list`의 버전별 지원을 확인하고, 조회할 수 없는 내용과 페이지는 누락으로 표시한다. `full` 역시 저장되지 않은 실시간 이벤트까지 복원한다는 뜻은 아니다.

공식 문서는 CLI로 해당 버전에 맞는 TypeScript/JSON 스키마를 생성할 수 있다고 설명한다. 구현 시 설치된 Codex 버전과 스키마를 확인하고, 페이지 조회·하위 스레드 연결·사용량·이벤트 복원 지원을 합성 데이터와 실환경에서 각각 검증한다. 실험적 필드는 명시적 opt-in이 필요할 수 있으며 기본 안정 API로 가정하지 않는다. [공식 문서](https://learn.chatgpt.com/docs/app-server), [Codex 플랫폼 설명](https://developers.openai.com/blog/codex-as-a-platform).

설치된 CLI 0.166.0의 생성 스키마와 현재 문서의 차이, 저장 기록 조회의 한계는 [별도 조사](../research/codex-app-server-schema.md)를 참고한다. 이는 서버 동작이나 실환경 지원을 검증한 결과가 아니다.

## 이벤트와 증거 모델

공통 이벤트는 최소한 `run_id`, `task_id`, `thread_id`, `parent_thread_id`, `agent_id`, `event_id`, `event_type`, `timestamp`, `source`, `verification_status`, `payload`를 고려한다. 식별자·시각이 출처에서 제공되지 않으면 null 또는 명시적인 `unknown` 상태로 둔다. 사람이 보기 좋도록 만든 내부 ID는 출처가 제공한 실제 ID와 구별한다.

`source`에는 어댑터와 원본 형식·버전, 수집 시점, 안전하게 참조할 수 있는 위치 또는 식별자를 보존한다. 전체 원본 본문이나 민감한 절대 경로를 기본 저장·내보내기하지 않는다. 정규화기는 관측 사실과 파생 판단을 구분하고, 지원하지 않는 필드·형식은 조용히 버리지 않고 미지원과 누락 범위를 보고한다.

분석 결과는 **Confirmed**(직접 관측한 사실), **Suspected**(규칙이 제시한 후보), **Unknown**(필수 근거 부족)으로 표시한다. 반복 호출 자체는 관측 사실일 수 있지만 불필요한 낭비였다는 결론은 별도 검증 전까지 의심이다. 테스트 프로세스 실행과 실제 테스트 통과를 구분한다.

사용량은 입력·출력·캐시·추론을 출처가 제공할 때만 각각 기록한다. 값이 없으면 0으로 바꾸지 않는다. 누적 갱신을 합산해 중복 계산하지 않고, 출처의 집계 의미를 확인할 수 없으면 총합을 미확인으로 둔다. 요청 모델·추론 강도는 실행된 모델의 증거와 별도 필드로 남긴다.

## 순서·중복·복구

- 출처가 안정적인 이벤트 ID를 제공하면 출처 범위를 포함해 중복을 식별한다. ID가 없을 때 페이로드가 같다는 이유만으로 두 행동을 동일 이벤트로 단정하지 않는다. 안전한 식별이 불가능하면 중복 가능성과 근거를 남긴다.
- 자식 스레드의 활동이 등록보다 먼저 도착하면 원래 ID와 미연결 상태를 보존하고, 실제 연결 근거가 도착할 때만 관계를 갱신한다. 이름이 비슷하다는 이유로 연결하지 않는다.
- 기록 누락·지원하지 않는 형식·페이지 조회 미완료·중단은 수집 결과의 불완전 사유와 범위로 표현한다. 누락률의 분모가 없으면 비율도 `unknown`이다.
- 재가져오기와 연결 재개는 기존 원본을 수정하지 않고 가능한 범위에서 재처리한다. 기록이 제공한 사실과 실시간에만 존재했던 알림의 차이를 표시한다. 복구 중 중복·순서 역전·부분 실패를 테스트한다.
- 실패·중단·완료는 출처의 명시적 상태로 구분한다. 상태가 없으면 성공으로 간주하지 않는다.

## 개인정보와 권한

기본 동작은 사용자가 지정한 원본의 읽기 전용 분석이다. 인증 파일·API 키·개인 대화 원문을 저장소나 공개 예제에 넣지 않으며 테스트에는 합성 자료를 사용한다. 파일 경로·명령·메시지에도 민감정보가 있을 수 있으므로 기본 내보내기는 필요한 메타데이터만 포함하고, 원문 보관이나 공개는 별도 사용자 선택과 검토를 요구한다. 마스킹이 모든 비밀을 탐지한다고 보장하지 않는다.

원본과 결과 저장 경로를 분리하고 원본을 수정하지 않는다. `workspace-write`와 전체 시스템 권한을 혼동하지 않으며 연결 오류를 이유로 샌드박스를 해제하지 않는다. Harness²와 EAT의 조사된 우회 옵션은 그대로 이식하지 않는다. 데이터 보존 기간·삭제 방식과 민감정보 처리의 구체 정책은 구현 전 별도 결정이 필요하다.

## 실험과 수용 기준

후속 실험은 Git 커밋, 과제, 환경, 검증 명령, 권한, 제한 시간, 모델 후보와 평가 데이터를 고정한다. 실패·재시도를 포함하고 과제 완료 품질, 시간, 관측된 사용량, 위임 수, 검증 결과와 누락 상태를 함께 보고한다. 정책 개발 데이터와 평가 데이터는 분리한다. 단일 실행 결과로 일반적 성능 향상을 주장하지 않는다.

단계 1 구현의 필수 검증은 합성 기록에 대한 단일·다중 에이전트, 순서 역전, 중복, 누락, 이름과 ID 불일치, 사용량 없음, 실패·중단, 연결 복원, 미지원 형식의 10개 시나리오다. 테스트는 실제 명령·결과를 기록한다. 실환경 Codex/WSL 연동은 별도 확인 전까지 미검증이며, 로컬 테스트 통과로 대체하지 않는다.

## 열린 결정

1. 설치된 Codex 버전에서 공식 페이지 조회·하위 스레드 관계·사용량을 어디까지 복원할 수 있는지 확인 필요.
2. 원본별 이벤트의 안정적 ID와 누적 사용량 의미를 확인한 뒤 중복·집계 규칙을 확정한다.
3. TypeScript·SQLite 드라이버·테스트 도구의 버전 및 배포 환경은 0.4에서 선정한다.
4. 대용량 기록의 처리 한계, 저장 수명과 개인정보 정책은 구현 Issue에서 검증한다.
5. 선행 도구 대비 효용과 허위 양성률은 서로 다른 과제의 반복 실험 전까지 확인 필요다.
