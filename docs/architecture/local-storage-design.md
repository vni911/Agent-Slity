# 1단계 로컬 저장 계층의 최소 범위

상태: turn writer·reader 부분 구현·나머지 저장 설계 · 확인일: 2026-11-24 · 최초 설계 [Issue #110](https://github.com/vni911/Agent-Slity/issues/110) · 최초 설계 기준 코드: `ffb90de693b1930bff8250284bbb47b36b122265`

writer 업데이트: [Issue #112](https://github.com/vni911/Agent-Slity/issues/112)의 `saveChildTurnCollectionJson(result, path)`와 `ChildTurnSnapshotWriteResult`는 publication_status, temp_cleanup_status, error와 cleanup_errors를 반환하며 수집 JSON에는 넣지 않는다. error는 invalid_input/already_exists/unsupported_storage/io_error 또는 null, cleanup_errors는 close_failed/unlink_failed다. 임시 삭제 실패 뒤 lstat 잔류는 pending, ENOENT는 complete, 잔류나 handle 정리 미확인은 unknown이다. 게시 후 정리 실패는 error:null과 cleanup_errors로 남긴다. 기존 대상 사전 lstat은 거부 최적화이고 동시 게시 방어는 link에 맡긴다. #112 당시 전용 reader와 exec 보완은 추가하지 않았다.

reader 업데이트: [Issue #114](https://github.com/vni911/Agent-Slity/issues/114)의 `readChildTurnCollectionJson(path)`는 기존 CLI의 byte reader를 공유하며 일반 파일·실제16MiB·fatal UTF-8/BOM·finally close와 parser를 연결한다. ChildTurnSnapshotReadError의 code는 invalid_input/read_failed/invalid_json이고 message는 고정이다. writer/라이브러리 reader는 경로 정책을 공유하되 기존 CLI의 인수·경로 정책과 배치64MiB 의미는 유지한다. CLI 저장·exec 보완·전체 저장 완료는 추가하지 않는다. 실제 환경·CI·한계는 각 Issue에 기록한다.

## 목적과 결정안

수집한 관측을 나중에 다시 읽어도 출처·수집 상태·불확실성이 바뀌지 않도록 보존한다. 팀 협업의 효율 보고서가 사용할 근거를 남기는 1단계 기반이며 팀 실행·효율 판단 기능 자체는 아니다. [상위 아키텍처](overview.md)의 저장 요구와 [합성 수용 검증](phase-one-acceptance.md)을 구현 Issue의 완료 기준으로 연결한다. 최초 #110은 설계만 제공했다. 현재는 #112 writer·#114 reader 구현과 후속 계획을 함께 기록하며, 아래 모든 저장 기능이나 환경 지원이 완료됐다는 뜻은 아니다.

권고안은 **사용자가 명시한 새 파일에 기존 형식의 JSON 스냅샷 하나를 보존하는 방식**이다. 파일마다 독립적인 관측이며 자동 병합·중복 제거·검색 인덱스는 두지 않는다. 첫 구현 대상은 이미 exporter와 parser가 있는 자식 turn 수집 결과다. 기존 exec 정규화 결과의 저장/재읽기는 별도 작업으로 남기며, turn 저장 하나만으로 전체 로컬 저장 계층이나 1단계 완료를 선언하지 않는다.

| 대안 | 장점과 비용 | 이번 결정안 |
| --- | --- | --- |
| 최종 경로에 직접 `wx` 쓰기 | 기존 exec `--output`과 비슷하고 단순하지만 쓰기 실패·중단 시 최종 이름에 부분 파일이 남을 수 있음 | 기존 호환 동작만 유지. 새 스냅샷 저장의 완료 계약으로 사용하지 않음 |
| 완성한 임시 파일을 덮어쓰기 없이 게시 | 기존 형식과 독립 관측을 유지하면서 쓰는 중인 내용을 최종 이름에서 읽는 것을 피하는 계약을 검증할 수 있음. 파일시스템 제약과 임시 파일 정리 상태가 필요 | 첫 구현의 권고안. 지원 대상 환경의 실패·동시성 검증을 통과해야 함 |
| SQLite 등 관리형 저장소 | 다중 관측의 조회·인덱스·관계 관리로 확장할 수 있으나 별도 스키마·마이그레이션·수명 관리 결정이 필요 | 이번 최소안에서 도입하지 않음. 성능 우위를 주장하지 않으며 이후 필요에 따라 별도 설계 |

## 형식별 현재 상태와 완료 조건

| 대상 | 현재 제공 | 추가로 필요한 저장 검증 |
| --- | --- | --- |
| `agent-slity.child-turn-collection`, version1 | exporter·parser·CLI 요약, #112 writer와 #114의 제한된 파일 reader. 실제 파일/경합/중단/왕복 검증은 각 Issue에 기록 | 지원 환경별 추가 근거와 형식별 수용 근거 갱신. turn 저장/읽기만으로 전체 저장 완료를 뜻하지 않음 |
| `agent-slity.normalization-results`, version1 | 기존 exporter/exec `--output`과 #116의 제한된 문자열 parser | 전용 파일 reader/writer에 게시 계약 적용. 기존 exporter/CLI에는 새 parser의 크기·개수 제한이 자동 적용되지 않음 |
| 요약 JSON·관계/중복 후보 출력 | 관측에서 파생하는 별도 출력 | 원래 수집 관측을 대체하는 저장 형식으로 채택하지 않음. 지원되는 근거를 다시 읽어 재계산하며 캐시 저장은 요구하지 않음 |

1단계 저장 완료 판정에는 **각 지원 형식**의 출처·원본 위치·명시적 ID·진단/미지원·불완전 상태를 보존하는 파일 왕복, 명시적 쓰기, 실패/덮어쓰기 경계와 재처리 검증이 필요하다. SQLite 도입이나 디렉터리 전체 검색 자체를 완료 조건으로 삼지 않는다. exec의 기존 새 파일 저장도 유효한 선행 기능이지만 그 사실을 강한 게시·재읽기 계약의 충족으로 바꾸지 않는다. 형식별 부족한 조건을 해소하기 전에는 전체 저장 완료를 표시하지 않는다.

## 첫 구현의 데이터 계약

- 하나의 `ChildTurnCollectionResult`를 기존 exporter로 검증·복사하고 그 JSON 문자열만 저장한다. 별도 wrapper·자동 ID·수집 시각·파일 경로·cursor·서버 stderr·원본 payload를 추가하지 않는다. 저장 시각과 관측된 실행 시각을 섞지 않는다.
- UTF-8 **전체 파일 최대16MiB**다. exporter 문자열에 BOM·LF를 추가하지 않는다. 같은 16MiB를 적용하는 기존 reader와 경계값에서 호환돼야 한다. JSON 문자열·버퍼·검증 복사본이 공존하므로 전체 메모리 상한을 뜻하지 않는다.
- `source_id`, `schema_reference`, `unverified`, thread/turn/item 관측과 위치·순서·중복을 기존 형식대로 유지한다. 추가 원문 속성은 exporter의 허용 목록 밖이므로 저장하지 않는다. parser가 허용하지 않는 version/schema/상태 조합은 추측해 변환하지 않는다.
- 초기화 오류, `partial`과 사유, 수집 대상 thread의 미지원, 자식의 `cleanup_status: unknown`, 관측 null과 실제0도 저장 가능한 결과다. **파일 게시 상태**와 **저장된 수집/자식 정리 상태**는 별개다. 수집 실패를 저장 실패로 바꾸거나 그 반대로 성공 수집으로 표시하지 않는다.
- 같은 내용·별칭·ID를 다른 파일명에 저장해도 각각 남긴다. 저장 횟수를 고유 실행·에이전트 수로 해석하지 않는다. 파일명·내용 일치·파싱 성공은 출처 인증이 아니다.
- 관계와 중복 후보는 지원되는 저장 관측에서 기존 순수 함수로 다시 계산한다. 예를 들어 thread 메타데이터로 부모 후보를 재계산할 수 있지만 turn 페이지가 기존 item 페이지 API와 같다고 간주하지 않는다. 늦은 부모가 도착해도 새 입력으로 새 후보를 만들며 이전 스냅샷·후보를 덮어쓰지 않는다.

## 명시적 저장과 게시 절차

아래는 #112 writer와 후속 구현에 적용하는 계약이다. writer의 public API는 상단 업데이트에 정의하며 CLI 저장 인수는 추가하지 않는다. 읽기/요약만으로 저장·서버 실행·디렉터리 탐색을 시작하지 않는다. 호출자는 기존의 신뢰하는 로컬 부모 디렉터리와 최종 파일 경로 하나를 명시한다. 부모 디렉터리를 자동 생성하지 않는다.

1. 인수·경로·자료형·exporter 구조/바이트 예산 검증을 먼저 마친다. Windows 장치·콘솔·ADS·확장/UNC 경로와 디렉터리 대상은 거부한다. 입력의 경로·원문·OS 오류 메시지를 반환 오류에 복사하지 않는다.
2. 같은 부모에 예측하기 어려운 임시 이름을 `wx`, 요청 mode `0600`으로 연다. 충돌 시 기존 임시 파일을 열거나 지우지 않는다. 이번 호출이 생성한 파일과 handle만 관리하고 디렉터리의 다른 파일은 정리하지 않는다.
3. exporter의 UTF-8 바이트 전체를 순차적으로 쓴다. 짧은 쓰기를 처리하고 0바이트 진행은 실패로 끝낸다. 파일 `sync`와 `close`가 모두 끝나기 전에는 최종 경로를 게시하지 않는다.
4. 같은 부모의 완성된 임시 파일을 `fsPromises.link(temp, final)`로 게시하는 안을 검증한다. 기존 최종 경로가 파일·디렉터리·symlink이면 변경하지 않고 충돌로 처리한다. 사전 `exists` 검사 후 rename으로 덮어쓰는 방식이나 `copyFile`/직접 쓰기 fallback은 허용하지 않는다. hard link가 지원되지 않거나 게시가 실패하면 지원되지 않는 환경/오류로 반환한다.
5. link 성공은 게시 완료 시점이다. 이후 임시 이름만 삭제한다. 임시 삭제 실패를 미저장으로 바꾸거나 게시된 최종 파일을 롤백 삭제하지 않는다. 최종 파일에는 이 writer가 다시 쓰거나 덮어쓰지 않는다.

같은 최종 이름으로 비적대적인 동시 저장을 시도하면 지원 대상 파일시스템에서 한 번만 게시돼야 한다. 각 호출은 자기 임시 이름만 정리한다. 다른 이름에 저장하면 서로 독립적이며 여러 파일에 걸친 원자적 트랜잭션은 제공하지 않는다. 재시도는 기존 파일을 덮어쓰지 않는다.

## 실패와 중단의 반환 계약

반환은 파일 계층의 `publication_status: published | not_published | unknown`, `temp_cleanup_status: complete | pending | unknown`과 원문 없는 고정 오류/경고 분류다. #112의 `ChildTurnSnapshotWriteResult` public 타입으로 제공한다. `not_published`는 **이 호출이 게시하지 않았음**을 뜻한다. 최종 경로에 다른 파일도 없다는 뜻은 아니다. 이 상태를 수집 결과 안의 `cleanup_status`에 넣지 않는다.

| 관측한 지점 | 게시 상태와 처리 |
| --- | --- |
| 자료/경로 검증 실패 또는 임시 생성 전 거부 | `not_published`. 새 파일 없이 종료. 다른 파일이나 원본을 변경하지 않음 |
| 임시 쓰기·sync·close 실패 | `not_published`. handle 정리와 자기 임시 파일 삭제를 시도하고 각각의 미완료를 보존. 정리 오류가 원래 오류를 가리지 않음 |
| 게시 시 기존 최종 이름과 충돌 | `not_published`. 기존 파일 보존. 자기 임시 파일만 정리하며 재사용/자동 덮어쓰기하지 않음 |
| link 성공을 관측 | `published`. 임시 삭제 성공이면 `complete`, 실패로 파일이 남으면 `pending`, 정리 여부 판단 불가면 `unknown`. 이미 게시한 파일은 유지 |
| 게시 호출의 결과가 불명확하거나 결과 전달 전 연결/프로세스 소실 | 확인된 성공을 받지 못한 호출자는 `unknown`으로 취급. 최종 파일 존재 여부를 추측해 성공으로 만들지 않음. 해당 프로세스가 강제 종료되면 반환 자체가 없을 수 있음 |

게시 전 강제 종료 시 임시 파일이 남을 수 있고 게시 직후 종료 시 최종 파일과 임시 이름이 함께 남을 수 있다. 파일 `sync` 성공만으로 디렉터리 항목까지 전원 장애에 내구성이 있다고 주장하지 않는다. 재시작 때 디렉터리를 훑어 자동 승격·삭제·재게시하지 않는다. 호출자는 명시한 최종 경로를 제한된 reader로 확인할 수 있지만, 존재/파싱/내용 일치만으로 이전 호출의 성공 응답이나 원래 실행의 진위를 복구할 수는 없다.

첫 구현에 자동 재시도·AbortSignal·중단한 cursor 재개는 요구하지 않는다. 반환이 없는 프로세스 중단과 정상 반환 상태를 구분해 합성 실패 주입으로 검증한다.

## 재읽기·보존·권한 경계

- #114의 전용 reader는 지정한 일반 파일만 읽고 열기 전/후 일반 파일·크기 확인, 실제 읽기16MiB+초과 판별1바이트, fatal UTF-8/BOM 거부, parser 검증과 close 완료를 확인한다. 기존 CLI와 내부 byte reader를 공유한다. symlink를 명시해 일반 파일을 가리키는 읽기 정책을 유지하며 자동 탐색은 하지 않는다. 라이브러리 경로 가드와 기존 CLI 경로 가드는 각각 유지하므로 CLI의 허용 경로가 모두 라이브러리에서 허용된다는 뜻은 아니다.
- 나중에 파일이 바뀌면 현재 바이트를 검증하며 일관된 과거 스냅샷을 인증하지 않는다. 불변은 writer가 게시 후 수정하지 않는다는 뜻이다. 외부 편집·하드 링크를 통한 수정·권한 있는 사용자의 교체를 차단하는 보장은 아니다.
- 보존 기한은 두지 않고 자동 만료·압축·동기화·업로드·백업·GC를 하지 않는다. 용량은 사용자가 관리하며 디스크 부족은 저장 실패로 처리한다. 삭제는 사용자가 지정 파일을 별도로 관리하는 범위로 남기고 첫 구현에 삭제 API를 넣지 않는다. 미정리 임시 파일도 사용자 확인 없이 일괄 삭제하지 않는다. 안전 삭제나 백업/다른 링크의 제거를 보증하지 않는다.
- ID·별칭·보고된 설정과 사용자가 정한 파일명은 민감할 수 있다. 허용 목록 저장은 익명화·암호화·비밀 탐지 기능이 아니다. 개인 기록·인증 파일을 공개 테스트에 사용하지 않는다.
- 임시 파일 `0600` 요청은 Windows 사용자별 ACL 격리를 뜻하지 않는다. 신뢰하는 부모의 접근 권한을 전제로 하며 ACL을 자동 변경하지 않는다. hard link는 같은 파일을 가리키므로 임시 이름도 같은 민감도를 가진다.
- 닫은 임시 파일을 경로로 link하는 방식은 **부모나 임시 경로를 악의적으로 바꾸는 공격을 방어하지 못한다**. 사전 검사나 realpath만으로 이 경합을 막았다고 주장하지 않는다. 이 설계의 동시성 검증은 신뢰하는 부모에서의 비적대적인 저장 경쟁에 한정한다.
- 검증 대상은 Windows의 로컬 NTFS 및 Linux의 hard link를 지원하는 로컬 파일시스템이다. 구체 OS·Node·파일시스템과 실제 결과를 구현 검증에서 기록해야 하며 현재 지원을 선언하지 않는다. 네트워크/동기화/가상 파일시스템은 첫 지원 범위 밖이다. UNC 거부만으로 모든 네트워크 마운트를 탐지했다고 주장하지 않으며 Linux 경로도 로컬 여부 자동 판별을 보증하지 않는다.

## 구현 단계와 합성 수용 계획

| 순서 | 별도 구현/검증 범위 | 통과 전 완료로 표시하지 않을 조건 |
| --- | --- | --- |
| 1 | 기존 turn exporter를 사용하는 제한된 명시적 파일 writer와 게시/정리 상태 | 정상 저장의 바이트/왕복, 기존 대상·경합·각 단계 실패·중단·원문 제외와 대상 OS/파일시스템 검증 |
| 2 | 전용 turn 파일 reader와 기존 parser/요약 연결 | 16MiB 경계·증가·손상 UTF-8/BOM·미지원 schema·일반 파일·close·이전 결과 불변. writer와 함께 검증하되 최초 writer와 읽기 API의 범위는 각 Issue에 명시 |
| 3 | exec 정규화 JSON 재읽기/구조·바이트 예산 및 게시 계약 적용 | 기존 `--output` 호환성을 별도로 검토하고 미완료 경계를 남김. turn writer의 추가만으로 기존 경로를 강화했다고 주장하지 않음 |
| 4 | 형식별 저장→재읽기→지원 후보 재계산/내보내기 수용 근거 갱신 | [10개 합성 시나리오](phase-one-acceptance.md)의 기존 결과와 저장 경로의 근거를 구분. 충족한 지원 범위에서만 저장 완료 판정 |

첫 구현에서 최소한 다음을 검사한다. 파일 부작용은 임시/최종 파일의 존재·바이트·원본 해시와 호출 반환 상태를 함께 기록한다.

1. 정상·초기화 오류·partial·cleanup unknown 결과를 저장해 기존 parser와 요약으로 비교한다. null/0·중복·미지원·위치·원문 제외를 보존한다.
2. 유효 JSON16MiB를 정확히 저장해 기존 CLI reader로 읽고 초과 자료는 새 파일 생성 전에 거부한다. BOM·LF가 추가되지 않았음을 실제 바이트로 확인한다.
3. 기존 파일·같은 원본 경로·디렉터리·symlink 대상, Windows 장치/ADS/확장/UNC 경로를 덮어쓰지 않는다. 잘못된 인수는 파일 작업 전 실패한다.
4. 같은 이름의 두 독립 프로세스 게시 경쟁에서 한 최종 파일만 온전하게 남고 충돌한 호출이 다른 호출의 파일을 정리하지 않는지 확인한다. 다른 이름은 둘 다 보존한다.
5. 짧은 쓰기·0진행·디스크 부족 상당 오류·sync·close·link·unlink 실패를 주입한다. 실패 주입은 실제 디스크 부족이나 모든 장치 오류의 증거와 구분한다. 게시 성공 후 임시 삭제 실패는 published/pending으로 남는다.
6. 임시 완성 전·게시 직전·게시 후 반환 전의 합성 자식을 종료한다. 부분 최종 파일을 만들지 않는 계약과 잔여 임시/최종 파일, 호출자의 unknown을 구분한다. 전원 장애 시험으로 표현하지 않는다.
7. hard link 미지원·권한 거부·부모 경로 소실 등에서 fallback과 외부 파일 삭제가 없는지 확인한다. 적대적인 부모 교체에 대한 방어 성공으로 확대하지 않는다.
8. 위 사례를 지원 대상 OS/파일시스템에서 실행하고 skip·미지원·미확인 범위를 공개한다. 로컬 모의 검사와 CI, 실제 저장 장치 관측을 구분한다. 개인 기록·실제 App Server는 필요하지 않다.

## 출처와 미확인 사항

공식 문서 확인일: 2026-11-19. 아래는 API 동작의 조사 근거이며 이 저장 알고리즘을 구현하거나 시험한 근거는 아니다.

- [Node.js 24.18.0 파일시스템 flags](https://nodejs.org/download/release/v24.18.0/docs/api/fs.html#file-system-flags): exclusive 생성과 네트워크 파일시스템의 제약. 사전 access 검사만으로 경합을 해결할 수 있다는 근거가 아니다.
- [Node.js link](https://nodejs.org/download/release/v24.18.0/docs/api/fs.html#fspromiseslinkexistingpath-newpath), [sync](https://nodejs.org/download/release/v24.18.0/docs/api/fs.html#filehandlesync), [권한](https://nodejs.org/download/release/v24.18.0/docs/api/fs.html#fschmodpath-mode-callback): hard link API, 장치별 flush 의미와 Windows 권한 차이. 파일 sync만으로 모든 장애의 내구성·Windows ACL 격리를 보증하지 않는다.
- [Microsoft CreateHardLinkW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createhardlinkw): NTFS의 파일 hard link와 같은 볼륨 제약. Node 경유 구현과 목표 환경 지원은 별도 검증이 필요하다.

이 설계의 채택·구현·실행 검증은 별개다. 구현 후에도 실제 기록의 완전 복원, 모든 파일시스템/권한/공격/전원 손실의 무결성, 사용량·품질·효율 측정은 보증하지 않는다. [Issue #91](https://github.com/vni911/Agent-Slity/issues/91)의 열린 상태와 특정 Codex/Linux 합성 기록에 한정된 검증 범위를 유지한다.
